# V3 Detailed Implementation Plan

Scope: cloud sync where users keep ownership of files in their cloud drives.
Primary success signal: app can open and save decks directly in user cloud with clear conflict handling.

## Step 1. Auth Foundation (OAuth)
Goal: provide secure account sign-in for cloud providers.

1. Substep 1.1: Integrate OAuth login shell (provider selection UI).
Deliverable: user can start auth for Google or Microsoft.

2. Substep 1.2: Complete token exchange and session storage.
Deliverable: authenticated session available to cloud API layer.

3. Substep 1.3: Add logout and token-expiry recovery flow.
Deliverable: expired sessions prompt clean re-auth.

## Step 2. Cloud File Connector Abstraction
Goal: standardize Drive and OneDrive operations behind one interface.

1. Substep 2.1: Define connector interface (list/open/save/create).
Deliverable: provider-neutral file API in app core.

2. Substep 2.2: Implement Google Drive connector.
Deliverable: can browse and open markdown/project files.

3. Substep 2.3: Implement OneDrive connector.
Deliverable: same operations work with Microsoft files.

## Step 3. Open/Save Cloud Workflow
Goal: make cloud editing feel equivalent to local editing.

1. Substep 3.1: Add Open From Cloud picker and recent file memory.
Deliverable: user can select a cloud file and load it.

2. Substep 3.2: Add Save and Save As to cloud destination.
Deliverable: edits can be written back to provider.

3. Substep 3.3: Add dirty-state prompt before navigation.
Deliverable: user is warned before losing unsaved changes.

## Step 4. Conflict Detection And Resolution
Goal: prevent silent overwrite when file changes remotely.

1. Substep 4.1: Track provider revision IDs in editor state.
Deliverable: save requests include expected revision.

2. Substep 4.2: Detect mismatch on save and block blind overwrite.
Deliverable: conflict state shown with clear message.

3. Substep 4.3: Add manual resolution flow (reload, duplicate, overwrite).
Deliverable: user can decide conflict outcome explicitly.

## Step 5. Offline And Recovery Behavior
Goal: ensure resilience under unstable connectivity.

1. Substep 5.1: Buffer unsaved edits locally when network fails.
Deliverable: edits are not lost during temporary outages.

2. Substep 5.2: Add retry queue for pending cloud writes.
Deliverable: saves are retried automatically when online.

3. Substep 5.3: Surface sync status indicators in UI.
Deliverable: user sees local, syncing, synced, or conflict states.

## Step 6. Cloud Security And Permissions
Goal: keep access minimal and auditable.

1. Substep 6.1: Request least-privilege scopes for each provider.
Deliverable: app uses minimal file permissions.

2. Substep 6.2: Add token handling hardening and secure storage review.
Deliverable: no tokens leaked to logs or URL state.

3. Substep 6.3: Add account disconnect flow and local data cleanup.
Deliverable: user can revoke access and clear local cloud cache.

## V3 Exit Criteria

1. User can authenticate with Google and Microsoft providers.
2. Open/save from cloud works with revision-safe writes.
3. Conflicts are detected and resolved via explicit user choice.
4. Temporary network failures do not cause content loss.
